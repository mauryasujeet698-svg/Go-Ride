# Go-Ride: Manual setup after code completion

This checklist is intentionally separate from source code. Do not commit API secrets, service-role keys, OAuth client secrets, signing keystores, or cron secrets.

## 1. GitHub Actions repository secrets

Open **Settings → Secrets and variables → Actions** and add:

- `SUPABASE_URL`: `https://rwbavyjpzyzijjwgtyqv.supabase.co`
- `SUPABASE_PUBLISHABLE_KEY`: the project's publishable key (safe for client apps, but configure through the build pipeline for consistency).
- `MAPBOX_ACCESS_TOKEN`: a public Mapbox token restricted to the Go-Ride Android application/package where supported.

The workflow only passes non-empty secrets to Flutter builds. If the Supabase URL/key are absent, the Admin and Driver Partner apps deliberately show a configuration page instead of pretending to be connected.

## 2. Google OAuth (all three apps)

Enable Google as a provider in Supabase Authentication, configure the Google OAuth client in Google Cloud Console, and add these exact app redirects to Supabase's redirect allow-list:

- Customer: `io.supabase.goride://login-callback/`
- Admin: `io.supabase.gorideadmin://login-callback/`
- Driver Partner: `io.supabase.goridedriver://login-callback/`

In Google Cloud Console, the authorized redirect URI for the Supabase provider is:

`https://rwbavyjpzyzijjwgtyqv.supabase.co/auth/v1/callback`

The Admin and Driver Partner Android platform folders and their callback intent filters are generated by GitHub Actions during APK builds. After adding OAuth settings, build all three APKs again and test sign-in on physical Android devices.

## 3. Grant the founder account Admin access

First sign in with Google once so the account exists in Supabase Auth. In the Supabase SQL Editor, find the account UUID:

```sql
select id, email from auth.users order by created_at desc;
```

Then grant the Admin role to the intended account only (replace the placeholder with the exact UUID):

```sql
insert into public.user_roles(user_id, role, status, granted_by, granted_at, revoked_at)
values ('<AUTH_USER_UUID>'::uuid, 'admin', 'active', null, now(), null)
on conflict (user_id, role) do update
set status = 'active', granted_at = now(), revoked_at = null;
```

Do not grant Admin to a public/test account. Signing in with Google alone never grants Admin privileges.

## 4. AI provider secrets

In Supabase **Edge Functions → Secrets**, add only the provider key you intend to use:

- `OPENAI_API_KEY`, or
- `GEMINI_API_KEY`, or
- `ANTHROPIC_API_KEY`.

Also add a strong randomly generated `AI_CRON_SECRET` (at least 32 random characters). Never put these keys in Flutter, GitHub source files, a database settings row, or a public issue.

The Edge Functions `ai-support-agent`, `ai-daily-report`, and `ai-security-audit` are deployed. The AI provider is initially disabled; after the key is added, choose the provider/model and enable the intended features from the Admin app.

The Admin setting **Estimated cost per AI request** is a conservative budget reservation, not an exact bill. Check actual usage and invoices in the provider's own console.

## 5. Schedule the 24-hour report and security audit

Enable the Supabase `pg_cron`, `pg_net`, and Vault extensions if they are not already enabled. Follow the template in `supabase/operations/schedule_ai_jobs.sql.example` after adding `AI_CRON_SECRET` to Edge Function secrets. Store the same secret in Vault, then schedule:

- Daily AI report: 00:00 India Standard Time (18:30 UTC).
- Security audit: 00:10 India Standard Time (18:40 UTC).

After scheduling, manually invoke each function once with the `x-cron-secret` header and confirm a job appears in the Admin app. Do not expose the cron secret in browser code or client apps.

## 6. Service-area and business configuration

In the Admin app:

1. Add each city/area/PIN-code service region.
2. For each area-specific region, enter a valid coverage centre and radius before enabling it. The current implementation uses a centre-radius circle, not official postal-boundary polygons.
3. Choose `subscription`, `commission`, or `disabled` for the ride service in that area.
4. Configure subscription plans in subscription areas.
5. Set global fare rules and review commission rates before enabling bookings.
6. Test a subscription area and a commission area separately. Check the stored ride pricing snapshot and financial ledger.

Changing a business model does not rewrite past rides. Existing subscriptions retain their price/duration snapshot.

## 7. Other integrations that require your decision or credentials

- **Mapbox:** Add the public access token as a GitHub Actions secret. Without it, maps fall back to OpenStreetMap tiles and the existing OSM-based geocoder/router.
- **Notifications:** Verify production push credentials, Android package registration and Admin notification delivery. Do not assume customer push delivery proves Admin delivery works.
- **Payments:** Select a payment provider if you want automated online subscription/commission settlement. Until then, subscription activation is manual and requires a verified payment/receipt reference.
- **Insurance:** Select an authorised insurer/partner, confirm policy terms and coverage, then integrate real policy issuance/confirmation. The app cannot claim a ride is insured until the partner confirms coverage.
- **App signing:** Configure a production Android signing keystore and store its passwords securely in GitHub Actions secrets. Current CI APKs are test/release builds, not certified Play Store releases.
- **Play Console:** Complete app signing, privacy policy, terms, account deletion, support contact, data-safety declarations and required legal/insurance review.
- **Driver verification:** Configure document upload/storage, actual verification rules and manual review procedures before accepting real drivers.
- **Production monitoring:** Set error/uptime alerts, backup and recovery procedures, and budget alerts for maps, notifications, database and AI providers.

## 8. Release gate

Do not launch until all three apps pass physical-device tests for Google sign-in, booking, driver dispatch/status updates, support escalation, area-specific pricing, subscription enforcement, notifications, and recovery from API/network failures. The security audit is an aggregate automated check, not a penetration test or a guarantee of security.
